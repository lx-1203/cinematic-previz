# Updream 接入、故障修复与低开销操作

## 先验收真实连接

运行本 Skill 的调用前同步检查，再按 [updream-mcp.md](updream-mcp.md) 初始化。服务能列出工具、单元测试通过，不等于浏览器已连接或真实画布可操作。

- 聊天没有 `updream_*` 工具：先核对已有 MCP 注册。已注册时不反复 setup；用插件项目的 `npm run diagnose` 做一次只读诊断，再由宿主重新加载工具。该命令检查已有服务，不配对、不重启、不创建工作区、不修改画布。
- `BROWSER_NOT_CONNECTED`：处理打开 Updream 的 Chrome/Edge 与扩展配对。Codex 内置浏览器里的项目页不能据此当作插件已连接的标签页；只使用插件真实返回的 tabId。
- 版本不符或 `BRIDGE_UPGRADE_REQUIRED`：核对本机、扩展及页面桥接版本；更新扩展后需重新加载并刷新项目页。刷新前保护未保存输入。
- 已连接但画布没启用/原生工具为零：按扩展入口启用目标画布，再只读复测。
- `CANVAS_OWNED`、`BUSY`、`UNKNOWN_OUTCOME`：遵循原来的归属、等待和读回规则；不为通过验收清理他人的锁或重复生成。

`npm run diagnose` 的 CLI 只用于诊断。每次独立 stdio 进程都有不同会话，不能用几个一次性进程分步执行 open_workspace → claim → write；写入必须使用保持连接的同一 MCP 客户端，并携带本任务自己的 workspaceId。

## 日常优先结构化接口

按任务选接口及目录精简参数见[低开销路由](updream-efficiency.md)。用户分配为维护窗口时留在本地源码/测试，不操作制作窗口的画布或上传。未连接扩展属于接入阻塞，不用大量UI重试作为插件性能测试。

工具可用后按任务读取最少数据：查目标先 find_nodes，编辑前 get_node 取完整草稿；使用 checked 更新及读回验证。无须每次加载完整工具手册、整页 DOM 或全部历史提示词；仅在模型或原生能力变化时查对应 Schema。

顺序独立写入可用已验证的 batch，不能假设批次会回滚。查询生成任务拉开间隔；状态未变时不反复打印长结果。上传、角色库、音频、报价或剪辑等接口未覆盖的部分才补界面操作，不宣称插件已覆盖未暴露能力。工具缺失时不静默回退到长期逐按钮操作。

## 故障反馈和修复闭环

跨使用者向开发者反馈时，按 [GitHub插件缺口反馈](github-feedback.md) 整理公开报告、查重与提交；本节的本地私有日志不能原样作为公开Issue正文。用户限定仅用插件时，能力缺口记录为待办，不回退界面操作。

1. 向用户简短反馈实际受阻动作、错误码和影响。把最小记录放到项目私有日志：本机/扩展/页面版本、工具名、脱敏参数、tabId/projectId/nodeId、预期/实际、是否可能已产生写入、最小复现。不要保存令牌、配对文件或整份聊天作为故障报告。
2. 区分环境接入和代码缺陷。没有浏览器连接不能当成业务代码 bug；版本诊断、结果拆包、并发或参数校验等缺陷应以复现和回归测试证明。
3. 用户授权插件维护时，可由当前代理或子代理作局部修复。先核对未提交变更并分配互不冲突的文件；必要时隔离工作区。修复代理不提交付费测试、不抢占制作画布、不擅自重启服务。
4. 先复现失败，再最小修复并运行相关回归；按项目的 global-self-review 要求审查代码和实际产物。真实连接、只读画布、写入及付费生成的验证状态分别记录，不能拿模拟测试代替实机结果。
5. 需刷新扩展/重启服务时先核对 activeMutations、pendingRequests、工作区认领和未知结果。执行中的请求不强制中断，确认拒绝不重试。已授权的本地修复不自动包含新的付费生成。
6. 把验证得到的新经验写入注册来源项目的 Skill/reference，再运行安装目录的同步脚本；只在 current/updated 后重读。安装端冲突保留原文件，不直接覆盖安装副本，不把未检查的 GitHub 远端称作最新。

交接记录至少包含：可用到哪一层、修复文件、实际运行的检查、仍需用户完成的浏览器接入步骤，以及是否已释放本任务工作区。
