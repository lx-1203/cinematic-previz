# 维护更新收尾与 GitHub 备份

## 普通调用和维护修改分开

普通用户使用技能前运行 `sync_from_project.py`，只是从已注册本机源码同步到安装副本；独立模式只核对当前本地包。`current`／`updated` 和文件 revision 只证明本机内容状态，`remote_checked=false` 不能证明 GitHub 已拉取、已上传或已是最新。普通调用不自动提交、推送，也不要求下载用户拥有作者仓库写权限。

维护者修改技能、脚本、参考规则或回写已验证经验后，必须进入本指南的收尾流程。先沿用本项目和当前会话已有的 GitHub 备份／发布授权；用户已要求“每次更新上传 GitHub”时，维护修改验证后自动完成授权范围内的提交、非强推上传和远端读回，不重复询问同一权限。代理不得自行在计划中增加“不发布远端”来缩减该要求。没有相应授权时不自行公开，说明待授权的目标和范围；不能把普通安装或使用技能当成公开发布授权。

仓库、分支、来源目录与权限从本项目的实际维护配置或已有会话记录取得，不把作者地址作为通用默认目标。`https://github.com/lx-1203/cinematic-previz` 是当前维护项目已知的仓库示例，不要求其他下载用户向这个仓库推送。目标或发布范围存在实质歧义时才集中澄清，已有明确登记直接沿用。

## 维护收尾顺序

1. **确认真实源码与改动范围。** 读取项目指令、Git 状态、已暂存和未暂存差异、未跟踪文件及现有 remote／分支。保留用户或其他代理的无关修改，列出本轮精确路径和应公开的文件；不把工作目录、安装副本或本地 ZIP 自动当 Git 仓库。
2. **验证并同步本机安装。** 按改动运行相关检查、global-self-review 和当前技能的本机同步门禁，读回安装文件与来源指纹。先解决实际失败，不把安装同步成功当作 GitHub 备份完成。历史已执行记录保留，不编造当前测试或远端状态。
3. **准备已授权的 Git 提交。** 使用现有 Git 和宿主已有授权；只暂存本轮已审的精确范围，核对暂存差异后提交，不使用整目录添加来夹带无关文件。不读取、输出或写入 token、私有密钥等凭据；按官方 Git／宿主登录流程恢复失效权限。不把安装端 `.skill-source.json`、锁、备份、`.local`、配对文件、账号数据、私有素材和含隐私的恢复日志提交到公共仓库。
4. **正常推送并处理远端变化。** 上传前读取准确目标分支的当前状态；需要时正常 fetch，再比较提交关系。只将本轮提交推送到已授权的仓库和分支，禁止强推、删除远端分支或用重写历史掩盖冲突。远端已前进时保留双方修改，按既有授权正常合并／变基并重新验证；不能安全确定时记录具体分叉，保留本地成果待处理，不反复盲推。
5. **读回远端并核对内容。** 推送返回成功后重新查询准确远端分支的 commit SHA，例如用 `git ls-remote`。从远端重新取得该提交，核对本轮应备份文件的树中路径和内容指纹，与已审源码清单逐项对应；仅看本地 commit、命令退出码或 GitHub 页面标题不算远端内容验证。远端同时有新提交时核实本轮提交的可达关系和当前文件内容，不把已经被改写的文件说成仍与本轮源码一致。
6. **保留备份回执并报告范围。** 在项目维护记录保存下列非敏感状态。已有授权要求上传时，只有远端 commit 与文件范围核验均成功才能把本轮维护备份标为完成；故障不阻止独立本地工作，但必须如实列出备份未完成项。

## 备份回执与阻塞状态

每次维护至少记录：

- 目标仓库、分支、远端 commit SHA 和实际核验时间。
- 本轮源码 revision、文件路径／内容指纹清单、验证命令及结果。
- 备份范围 `skill_only` 或完整插件范围；安装同步状态与 GitHub 状态分别列出。
- 产物若已生成，记录其来源 revision、路径、SHA256、真实发布地址与状态；本地 ZIP 不冒称已发布安装包。

这份回执是“备份成功的证据”，不包含账号认证凭据。缺少 Git 目录、远端配置、写权限、网络或存在未解决分叉时，记录 `backup_pending`、准确失败阶段与错误，以及当前已保存的源码／commit。不能用本机 `current`、测试通过、版本号或 ZIP 存在替代上传证据，也不能把仍待备份的维护任务报为全部完成。故障解决后沿用授权续做，从已有提交和回执恢复，避免重复提交相同改动。

源码恢复目录若没有 `.git`，保留原目录与备份；按已授权维护范围取得真实仓库 clone，核对其目录布局，再映射本轮文件。保留远端已有的无关文件和历史，不在缺少来源的恢复目录伪造原历史，不将旧分享快照冒充当前完整源码。无法取得真实仓库时保持 `backup_pending`，说明缺少的条件。

## 内容版本、技能备份和完整插件发布

`release.json` 中历史 `skillVersion`／`pluginVersion` 字段和 SKILL 元数据表示内容版本及配对声明，不能单独证明 GitHub 发布、Bridge 源码存在或安装包可重建。保留原字段，不为掩盖未发布状态改版本；内容 revision、远端 commit 和产物指纹各自记录。

仅备份技能时明确标 `skill_only`。完整插件备份／发布必须同时具备该版本的技能、Bridge server／extension、依赖与安装／打包脚本，并核对版本和文件清单；若声称已发布安装包，还须验证包来自这些源码及真实远端产物。缺任一部分就不能称完整插件已发布。

当前恢复维护源中的本机技能内容为 0.6.0，配对声明同为 0.6.0；Bridge 当前源码未恢复，不能据此把技能备份标成完整 0.6.0 插件发布。恢复或重建 Bridge 是另一个有明确范围的工作，不用旧 0.3.0 分享快照填充版本缺口。首次技能备份可以完成 `skill_only` 范围，但保留完整插件范围的未完成状态。
